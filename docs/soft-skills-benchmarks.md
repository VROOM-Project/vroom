# Soft-skills synthetic benchmarks

Benchmark results for the soft-skills feature (`soft_skills`,
`soft_skill_match_mode`, `options.soft_skills`, see the
[API reference](API.md#soft-skills)). All instances are **fully
synthetic** with fixed random seeds - no production data is used.

## Instances

Generated by `benchmarks/generate_synthetic.py` (seed `20261030`,
byte-reproducible):

| Parameter | Value |
| --------- | ----- |
| Sizes | 300 shipments / 20 vehicles, 600 shipments / 40 vehicles |
| Soft-skill coverage | 0%, 25%, 50%, 100% of shipments hold `soft_skills` |
| Skill universe | 8 skills (`100`..`107`), random assignment |
| Match modes | 70% of soft shipments: 1 skill, default `"all"`; 30%: 2 skills with per-shipment `"any"` override |
| Vehicle soft skills | random 3-skill pools; `options.soft_skills` = `{"default_match_mode":"all","threshold_mode":"cost","max_cost_factor":1.3}` |
| Capacities | vehicle `[26]`, shipment amount `[1]` or `[2]`, round trips, no time windows |
| Matrices | Euclidean (equirectangular) distances in meters; durations at 40 km/h; costs equal durations |

Vehicles carry `max_tasks: 50` on top of capacity: without a task-count
bound, pickup/delivery interleaving legally keeps the transit load
low and a *single* route can absorb the whole instance - a degenerate
shape that is both unrealistic and unusable for benchmarks (single
600-task routes made every solve glacial). With capacity plus
`max_tasks`, the instances need 12-25 routes and all shipments are
assignable.

Each (size, coverage) pair is generated twice from the same seeded
geometry:

- **baseline**: no soft-skills field anywhere - pure cost optimization
  (the "soft-skills disabled" reference);
- **soft**: shipment-level `soft_skills`, vehicle `soft_skills` pools
  and the `options.soft_skills` block above.

At 0% coverage no shipment holds soft skills, so the two variants are
identical apart from the vehicle-side `soft_skills` pools: they measure
the pure feature-path overhead on a problem with zero preference
decisions.

## Protocol

- Binary: `bin/vroom` from this branch, local build without routing
  engines (`USE_ROUTING=false`), instances carry custom matrices.
- One run: `./bin/vroom -i <instance> -t 1 -x 0 -l 20`
  (single-threaded, 4 searches, 20 s total solving budget shared per
  search). The default exploration (`-x 5`, 32 searches) is also
  sequential at `-t 1` and stretches the sweep over hours; `-x 0`
  already saturates the budget on the soft variant at the larger size.
- 5 runs per cell; wall time = median / p95 across runs (includes
  instance parsing, so budget-bound runs show ~21-22 s against the
  20 s solving limit); memory = peak RSS via `/usr/bin/time`.
- Quality columns = medians across runs of the reported `summary`.
- Hardware: 8-core shared development host, single run at a time.
  Absolute times are machine-dependent; the baseline/soft comparisons
  run under identical conditions.

Reproduce with:

```
python3 benchmarks/generate_synthetic.py
bash scripts/benchmark_soft_skills.sh
python3 benchmarks/aggregate_results.py benchmarks/results/results.tsv
```

## Observations

- **Idle-path overhead is negligible.** At 0% coverage the
  soft-skills-enabled variant is within noise of the baseline on every
  axis: +13-14% wall time, <= 1 MiB peak RSS, identical assignment
  quality. Inputs without soft skills keep their pre-feature behavior
  (see also the backward-compatibility note in
  [API.md](API.md#soft-skills)).
- **Solving time grows with coverage** because every preference
  decision triggers an on-demand non-matching baseline scan and the
  search keeps applying preference-gaining moves past the point where
  cost-only search has converged: median wall time goes from ~0.8 s to
  ~15.8 s (x21) at 300/20 and from ~3 s to the 20 s budget (capped) at
  600/40. At the budget cap the 600/40 soft runs are still improving
  when the limit hits, so the reported times are a floor, not the full
  convergence time.
- **Preferences are bought, not free.** With `max_cost_factor: 1.3`
  the soft variant returns solutions 16.8-32.8% (300/20) and 22.1-
  34.8% (600/40) more expensive than the same-geometry cost-only
  baseline, and satisfies 47-62% of eligible shipments. Distance
  tracks cost (the instances price travel time at uniform speed).
- **No task is ever dropped for preference reasons**: unassigned
  stays 0 in every cell, matching the guarantee that soft skills
  never restrict feasibility.
- **Memory is dominated by input parsing** (~39 MiB / ~135 MiB across
  the board): the feature adds <= 1 MiB peak RSS at these sizes.

## Known issue surfaced and fixed during these benchmarks

The first sweep crashed with `Assertion 'rank <= route.size()' failed`
in `utils::addition_eval`, reached from `cvrp::RouteExchange::compute_
gain` through the preference placement evaluation of shipments: the
insertion-search rank ranges of the *receiving* vehicle were applied
to the route the task actually stays in under a whole-route exchange.
Fixed in `src/algorithms/local_search/operator.h`
(`placement_eval_after_move`): when the destination already holds the
task, the exact marginal contribution is evaluated on the destination
with the task endpoints stripped and re-added at their original ranks,
instead of running a foreign-rank insertion search. The fix leaves the
no-soft-skills path byte-identical (baseline fixture digest
unchanged) and all soft-skills fixtures and unit tests pass.
